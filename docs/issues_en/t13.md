## Attestor Pool Architecture

### Overview

**Attestors** are validators selected via VRF to attest to data availability (DA) for each anchor.

**Key Parameters:**
- **M**: Target attestor pool size (typical: 128, range: 64-256)
- **Epoch**: Time period for VRF seed stability
- **VRF Seed**: Derived from `(network_id, last_anchor_id)`
- **Selection**: Top M candidates by VRF score, subject to eligibility

**Workflow:**
```
1. VRF Sampling: Select M attestors from validator set
2. Attestation: Each attestor signs DA commitment
3. Aggregation: Combine M signatures into single aggregate signature
4. Payout Calculation: Distribute attestor fee share equally among M
5. Claim Path: Generate Merkle proofs for each attestor
6. Claim Verification: Attestors submit claims with proofs
7. Payout: Verified claims trigger payout disbursement
```

### Attestor Selection Process

**Input:**
- `m`: Target pool size
- `current_anchor_index`: Current blockchain height
- `epoch_len`: Anchors per epoch
- `network_id`: Network identifier
- `last_anchor_id`: Previous anchor ID
- `candidates`: List of eligible validators with VRF proofs
- `params`: Rotation parameters (cooldown, attendance threshold)

**Output:**
- List of `m` selected attestors (SelectedSeat)

**Algorithm:**
```
1. Derive epoch = floor(current_anchor_index / epoch_len)
2. Derive seed = BLAKE3("pc:vrf:seed:v1\x01" || network_id || last_anchor_id)
3. For each candidate:
   a. Check eligibility (attendance >= threshold, cooldown satisfied)
   b. Verify VRF proof against (seed, epoch)
   c. Extract VRF score (32-byte hash)
4. Sort candidates by VRF score (ascending)
5. Apply anti-collocation (one attestor per operator_id)
6. Select top m candidates
7. Return selected attestors
```

## VRF Sampling (M≈128)

### Basic Sampling

**Function:** `attestor_sample_vrf(m, current_anchor_index, epoch_len, network_id, last_anchor_id, candidates, params)`

**Properties:**
- Deterministic: Same inputs → same output
- Unpredictable: VRF prevents pre-computation
- Fair: All eligible candidates have proportional chance based on VRF randomness
- Anti-collocation: At most one attestor per operator

**Typical Usage:**
```rust
let m = 128;
let selected = attestor_sample_vrf(
    m,
    current_anchor_index,
    epoch_len,
    network_id,
    last_anchor_id,
    &candidates,
    &params,
);
assert!(selected.len() <= m);
```

### Fair Sampling with Caps

**Function:** `attestor_sample_vrf_fair(m, ..., recent_op_selection_count, cap_limit_per_op, perf_index)`

**Additional Parameters:**
- `recent_op_selection_count`: HashMap tracking recent selections per operator
- `cap_limit_per_op`: Hard cap on selections (e.g., 5 out of last 100 rounds)
- `perf_index`: Performance score per operator (higher = better)

**Sort Order:**
```
1. VRF score (ascending, lower is better)
2. Performance index (descending, higher is better)
3. recipient_id (ascending, deterministic tiebreaker)
```

**Cap Enforcement:**
- Operators with `count >= cap_limit_per_op` are excluded before VRF scoring
- Prevents single operator from dominating attestor pool over time
- Promotes operator diversity and decentralization

## Signature Aggregation

### BLS Aggregate Signatures

**Purpose:** Combine M individual signatures into a single aggregate signature for efficient verification.

**Benefits:**
- Constant-size signature (96 bytes) regardless of M
- Single verification operation for all M attestors
- Bandwidth-efficient (96 bytes vs M*96 bytes)

**Functions:**
```rust
pub fn attestor_aggregate_sigs(parts: &[[u8; 96]]) -> Option<[u8; 96]];
pub fn attestor_fast_agg_verify(msg: &[u8], agg_sig: &[u8; 96], selected: &[SelectedSeat]) -> bool;
```

**Message Construction:**
```rust
pub fn attestation_message(network_id: &NetworkId, epoch: u64, topic: &[u8]) -> Vec<u8> {
    const DOMAIN: &[u8] = b"pc:attest:round:v1\x01";
    DOMAIN || network_id(32) || epoch(8, LE) || topic
}
```

**Workflow:**
```
1. Each attestor signs attestation_message with their BLS secret key
2. Aggregator collects M individual signatures
3. Aggregator calls attestor_aggregate_sigs() → single 96-byte signature
4. Verifier calls attestor_fast_agg_verify() → boolean result
```

**Performance:**
- Aggregation: O(M), ~500ms for M=128
- Verification: O(M) pairing operations, ~1-2s for M=128

## Claim Path & Merkle Proofs

### Payout Calculation

**Equal Distribution:**
Attestor fee share is distributed equally among M selected attestors.

```rust
pub fn compute_attestor_payout(
    fees_total: Amount,
    params: &FeeSplitParams,
    attestors: &[[u8; 32]],  // recipient_ids
) -> Result<PayoutSet, ConsensusError>
```

**Formula:**
```
attest_pot = fees_total * params.p_att_bp / 10000
per_attestor = attestor_pot / M

PayoutSet = [
    PayoutEntry { recipient_id: attestors[0], amount: per_attestor },
    PayoutEntry { recipient_id: attestors[1], amount: per_attestor },
    ...
    PayoutEntry { recipient_id: attestors[M-1], amount: per_attestor },
]
```

**Rounding:**
- Integer division may leave remainder
- Remainder is distributed to first `(attestor_pot % M)` recipients
- Ensures sum of payouts == attestor_pot exactly

### Merkle Tree Construction

**Purpose:** Enable attestors to prove their payout inclusion with log2(M) hashes.

**Structure:**
```rust
pub struct PayoutMerkleTree {
    pub leaves: Vec<Hash32>,       // Hashes of PayoutEntry
    pub nodes: Vec<Vec<Hash32>>,   // Internal nodes (level 0 = leaves)
    pub root: Hash32,              // Merkle root
}
```

**Leaf Hash:**
```
leaf_hash = BLAKE3("pc:payout:leaf:v1\x01" || recipient_id(32) || amount(8, LE))
```

**Internal Node Hash:**
```
internal_hash = BLAKE3("pc:payout:node:v1\x01" || left_child(32) || right_child(32))
```

**Construction:**
```
1. Hash all payout entries → leaves
2. If odd number of leaves, duplicate last leaf
3. Pair up leaves, hash each pair → level 1
4. Repeat pairing and hashing until single root remains
5. Root is the payout_root published on-chain
```

### Merkle Proof Generation

**Function:**
```rust
pub fn generate_claim_proof(
    payout_set: &PayoutSet,
    recipient_id: &[u8; 32],
) -> Result<AttestorClaim, Error>
```

**Output:**
```rust
pub struct AttestorClaim {
    pub recipient_id: [u8; 32],
    pub amount: Amount,
    pub payout_root: Hash32,
    pub merkle_proof: Vec<Hash32>,  // log2(M) sibling hashes
    pub leaf_index: u32,
}
```

**Proof Structure:**
- For M=128, proof size = ceil(log2(128)) = 7 hashes = 224 bytes
- Proof consists of sibling hashes along path from leaf to root

**Example (M=8):**
```
        Root
       /    \
      A      B
     / \    / \
    C   D  E   F
   /|  /|  /|  /|
  0 1 2 3 4 5 6 7   (leaf indices)

Proof for leaf 2:
- Sibling at level 0: leaf_hash(3)
- Sibling at level 1: D
- Sibling at level 2: B
Proof = [hash(3), D, B]
```

### Merkle Proof Verification

**Function:**
```rust
pub fn verify_claim(
    claim: &AttestorClaim,
    expected_root: &Hash32,
) -> Result<bool, Error>
```

**Algorithm:**
```
1. Compute leaf_hash from (recipient_id, amount)
2. current_hash = leaf_hash
3. For each sibling in merkle_proof:
   a. If leaf_index is even: current_hash = hash(current_hash || sibling)
   b. If leaf_index is odd:  current_hash = hash(sibling || current_hash)
   c. leaf_index = leaf_index / 2
4. Return current_hash == expected_root
```

**Security:**
- Infeasible to forge proof without knowing preimage
- Proof size logarithmic in M (efficient for large pools)
- Verification complexity O(log M)

### Claim Submission

**HTTP Endpoint:**
```
POST /attestor/claim
Body: AttestorClaim (JSON)
Response: { success: bool, tx_hash?: string }
```

**Validation:**
1. Verify Merkle proof against on-chain payout_root
2. Check recipient_id not already claimed (double-claim prevention)
3. Verify claim within timeout window (e.g., 1000 anchors)
4. Validate amount matches proof

**Double-Claim Prevention:**
- Track claimed recipient_ids per anchor in database
- Reject duplicate claims
- Invalidate claims after timeout

## Fair Distribution

### Equal Payout Split

**Property:** Each of M attestors receives equal share of attestor pot.

**Formula:**
```
attest_pot = fees_total * p_att_bp / 10000
base_amount = attestor_pot / M
remainder = attestor_pot % M

For i in 0..M:
    amount[i] = base_amount + (1 if i < remainder else 0)
```

**Invariant:**
```
sum(amount[0..M]) == attestor_pot
```

### Fairness Over Time

**Mechanisms:**
1. **VRF Randomness:** Prevents predictability of selection
2. **Anti-Collocation:** One attestor per operator per round
3. **Caps:** Limit selections per operator over rolling window
4. **Performance Index:** Reward reliable operators with higher selection probability
5. **Cooldown:** Prevent rapid re-selection of same validator

**Measurement:**
- Track operator selection count over N epochs
- Expected: Each operator selected ≈ (M * N) / (total_operators)
- Variance should be within acceptable bounds

## Performance Characteristics

### Computational Complexity

**VRF Sampling:**
- Eligibility filtering: O(n) where n = candidate count
- VRF verification: O(n * VRF_cost) where VRF_cost ≈ 1-2ms
- Sorting: O(n log n)
- Selection: O(M)
- **Total:** O(n log n) + O(n * VRF_cost)

**Signature Aggregation:**
- Aggregation: O(M) BLS point additions
- Typical: ~500ms for M=128

**Signature Verification:**
- Fast aggregate verify: O(M) pairing operations
- Typical: ~1-2s for M=128

**Payout Calculation:**
- Division and distribution: O(M)
- Typical: < 1ms for M=128

**Merkle Tree:**
- Construction: O(M)
- Proof generation: O(log M)
- Proof verification: O(log M)
- Typical: < 10ms for M=128

### Scalability Limits

- **Recommended M:** 64-256
- **Typical M:** 128
- **Max M tested:** 256
- **Candidate pool:** Up to 10,000 validators
- **Merkle proof size:** log2(M) * 32 bytes (224 bytes for M=128)

### Optimization Strategies

1. **Parallel VRF Verification:** Verify proofs concurrently
2. **Cached Merkle Trees:** Reuse trees across claims
3. **Batch Claim Processing:** Process multiple claims together
4. **Lazy Proof Generation:** Generate proofs on-demand
5. **Compressed Proofs:** Use proof compression for large M

## Security Considerations

### VRF Security

- **Unpredictability:** VRF output unpredictable without secret key
- **Uniqueness:** Each (seed, epoch, bls_pk) → unique VRF output
- **Verifiability:** Anyone can verify VRF proof with public key

### Sybil Resistance

- **Anti-Collocation:** One attestor per operator_id
- **Caps:** Hard limits on selections per operator over time
- **Cooldown:** Prevents rapid re-selection
- **Stake-Weighted (future):** Higher stake → higher selection probability

### Claim Security

- **Merkle Proof Binding:** Infeasible to forge valid proof
- **Double-Claim Prevention:** Track claimed recipient_ids
- **Timeout Enforcement:** Claims expire after N anchors
- **Amount Validation:** Claimed amount must match proof

### Griefing Resistance

- **Signature Aggregation:** Single invalid signature invalidates aggregate
  - **Mitigation:** Identify and slash invalid signers
- **Claim Spam:** Many invalid claims submitted
  - **Mitigation:** Rate limiting, proof verification before storage

## Troubleshooting Guide

### Empty Attestor Pool

**Symptoms:** `attestor_sample_vrf()` returns empty Vec

**Causes:**
1. All candidates in cooldown → Reduce `cooldown_anchors`
2. All candidates below attendance threshold → Reduce `min_attendance_pct`
3. All VRF proofs invalid → Check proof generation
4. M=0 → Check parameter configuration

### Signature Verification Fails

**Symptoms:** `attestor_fast_agg_verify()` returns false

**Causes:**
1. Mismatched message → Verify attestation_message construction
2. Wrong public keys → Check selected attestors match signers
3. Invalid signature → Identify and remove invalid signer
4. Aggregation error → Verify all individual signatures valid first

### Claim Verification Fails

**Symptoms:** `verify_claim()` returns false

**Causes:**
1. Wrong payout_root → Verify root matches on-chain value
2. Invalid Merkle proof → Regenerate proof
3. Amount mismatch → Check payout calculation
4. Corrupted proof data → Verify serialization/deserialization

### Unfair Distribution

**Symptoms:** Some operators selected far more often than others

**Causes:**
1. Caps not enforced → Check cap_limit_per_op
2. VRF bias (rare) → Investigate with statistical tests
3. Insufficient operator diversity → Increase validator set
4. Performance index too dominant → Adjust weighting
